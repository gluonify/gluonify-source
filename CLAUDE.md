# CLAUDE.md: guidance for an AI assistant working on this project

This repository is the **starting point** for a Quarkus 4 service that runs on Gluonify. Read `README.md` first: it explains everything, step by step (also available as `README.fr.md`, `README.es.md`, `README.it.md`, `README.de.md`). This file summarizes what you must not break.

Shared context for every gluonify-* repository (rules, build order, pitfalls, conventions, Edge model): `/Users/a/dev/gluonify/CLAUDE.md`, loaded automatically with this file (written in French).

## Commands
- `mvn quarkus:dev`: development (hot reload, UI at http://localhost:8080, **no token needed**: the "dev" identity exists only in this profile).
- `mvn test`: 121 Java tests (REST, stores, webhooks, platform, documents, sign-in configuration, conformity). The UI is tested separately: `cd src/main/webui && npm test` (53 tests).
- The Gluonify SDK (`gluonify-plasma-quarkus`, test scope `gluonify-plasma-testing`; `gluonify.sdk.version` is `0.7.2`, published on sea; since 0.7.1 its client modules carry the markers `META-INF/gluonify/services/<service>` from which Bup infers `uses`) comes from the Maven repository of gluonify-sea (`gluonify.sea.maven.url` in `pom.xml`, default `https://images.gluonify.io/maven`); to build against another copy: `mvn verify -Dgluonify.sea.maven.url=file:///path/to/repository`.
- Native (what Gluonify runs): `docker build --target out --output type=local,dest=dist -f Dockerfile.build .` -> `dist/gluonify-source`.
- Rename the project: `python3 scripts/rename.py <groupId> <artifactId> [<package>]`, then `mvn test`.
- Java 25, Quarkus 4.0.0.Beta1, Jackson 3 (`tools.jackson.databind`, not `com.fasterxml`), GraalVM native (Mandrel 25).

## Platform rules (Gluonify's builder enforces them; `ConformityTest` checks them on your side)
- `quarkus-smallrye-health` is mandatory (R-SANTE). No plaintext secret in `application.properties`: use `${VARIABLE}` or `${app.key}` (R-SECRET). No `.env`, `*.pem`, `*.p12`, `*.jks` (R-FICHIER-SENSIBLE). No `quarkus-container-image-*` (R-IMAGE). `quarkus.http.host` never on loopback (R-ECOUTE). Native compilation never disabled (R-NATIF).
- **All configuration comes from the environment** (variables provided by the platform or its vault). Never hard-code a service address, a port or a password.

## Known pitfalls (do not fall into them again)
- **Native**: no `HttpClient` and no `SecureRandom`/`Random` in a `static` field (state frozen at build time): create it on first use. Read third-party JSON as a tree (`JsonNode`) rather than into undeclared classes. A type (de)serialized by Jackson outside a REST signature must carry `@RegisterForReflection`.
- **`/distributed/std`**: never rewrite a file or rename a directory that was just written; write NEW files under their final name. A directory listing can lag by ~3 s behind another replica.
- **Photon webhooks**: a 2XX status acknowledges, anything else causes a replay; be idempotent on `X-Gluonify-Event-Id`, across ALL replicas (`EventLedger`: never an in-memory map alone; files = `CREATE_NEW` of a new file, graph = uniqueness constraint).
- **Vault**: the `APP_` prefix exists only in the `<uuid>.app` space obtained with `"top": true` in the app spec; with a literal `topNamespace` keys arrive unprefixed.
- **Sign-in of the UI**: the UI is a public Charm client (authorization code + PKCE) through `createAuth` of the kit `@gluonify/ui`, vendored in `src/main/webui/vendor/gluonify-ui` (refresh it with `gluonify-ui/scripts/sync-vendor.sh <repo> src/main/webui`, never edit it). The password is typed on Charm's page only: never add a password field or a pasted-token box back. The client id and Charm's PUBLIC endpoints come from `GET /api/auth-config` (`AuthConfigResource`, `source.auth.*`, `GLUONIFY_SOURCE_OIDC_CLIENT_ID`, Charm base derived from `GLUONIFY_SOURCE_OIDC_ISSUER` unless `GLUONIFY_SOURCE_CHARM_PUBLIC_URL`), never from `GLUONIFY_SERVICE_CHARM_URL` (internal). Signed out, the UI shows only the explanation and the Sign-in button; `signInRequired: false` (OIDC off, `quarkus:dev`) shows everything.
- **Security**: `DevAuthentication` exists only in the `dev` profile (`@IfBuildProfile`). Do not extend it to production. Roles come from the Charm token (`source:read`, `source:write`).
- **Documents (Crystallon) are OPTIONAL and need NO configuration**: the SDK (`gluonify-plasma-quarkus`) produces the `CrystallonClient` and finds its address and token by itself (platform: `crystallon` in `uses`, inferred by Bup from the SDK marker or declared in a spec deployed by hand, the application's own token, file renewed by the node agent and re-read at every call; your machine: `gluonify login <zone>`; tests: `GluonifyTestServices.start()`/`close()` through `GluonifyTestServicesResource`). Never add a URL, a token or a token-file property back. `Documents` asks `GluonifyServices.optional("crystallon")` and injects `Instance<CrystallonClient>`: when Crystallon is not available there is no client, `POST /api/documents/invoice` answers 404 and nothing else changes: keep it that way (tests and the rest of the app must not need Crystallon; the pom points `GLUONIFY_HOME` at an empty folder so a real `gluonify login` never leaks into tests). The files of `documents/generated/` are generated by Crystallon's "Code" tab: regenerate them, never edit them; every record of a generated payload goes into `DocumentsReflection` (native-only failure otherwise, guarded by `DocumentsReflectionTest`). The template itself is versioned in `crystallon/templates/gluonify-invoice.json` (Crystallon's export format: the template with its exact `name` and `description` at the root) and the builder installs it at deployment (`created|unchanged|updated|differs`, never overwritten when the payload changes): change it in the console, export it, replace the file, regenerate the code and commit both; `CrystallonTemplateFileTest` checks the name and the top-level fields against the generated payload.
- **Which token Crystallon receives** = the application's own token (a Crystallon refusal is a 502: the caller cannot fix it). The caller's token ("forwarding") is NOT the default: it is an optional snippet in the README (an own `CrystallonClient` bean with `CrystallonTokens.forwarding`, which replaces the default one). Gdown and Charm are not covered by the SDK yet and stay configured by URL (`source.graph.url`, `quarkus.oidc.auth-server-url`).
- **`gluonify.json` = only the services the SDK cannot detect**: Bup sends `uses` and `gdownDatabase` to `PUT /apps/<name>`, which REPLACES the whole spec. Since SDK 0.7.1 Bup infers `uses` at build time from the markers of the SDK jars on the runtime classpath (`gluonify-plasma-crystallon-client` -> `?crystallon`) and merges them with the declared ones. So `gluonify.json` declares `["charm", "gdown"]` (OIDC and Cypher over HTTP, not reached through the SDK) and never `crystallon`; declared plus inferred must equal the `uses` of `deploy/appspec.json`, which keeps `crystallon` because a spec deployed by hand is not inferred (`DeploySpecsTest` checks both, and that the marker is on the classpath). Declare a service in `uses` only when the code reaches it outside the SDK (a direct HTTP call to another application, Charm for OIDC); without the file a build would remove `charm` and `gdown` from the application.
- Code comments are in **English** in this repository; the README exists in five languages (English by default) and this file is English only. Keep commit messages plain.

## Where to change what
`NotesResource` = the model of a REST resource; `NoteStore` + `NoteStores` = where to plug in a store; `SourceConfig` + `application.properties` = configuration; `WebhookResource` = receiving Photon; `PlatformResource` = platform variables and calling another service; `documents/` = an optional integration with an SDK client (`DocumentsResource` + `CrystallonClients` + `TokenMode` + `InvoiceMapping`; `generated/` is Crystallon's output); `gluonify.json` = the services the builder cannot infer (declared at deployment); `src/main/webui` = the Vue UI (Quinoa).
